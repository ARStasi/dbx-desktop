## Destination

Define a first-version desktop app concept for developers using paid Azure Databricks, with clear workflows and verified programmatic integration paths. Finish with decisions and a portable implementation handoff that can be taken from the current Mac to a Windows development machine.

## Notes

User-confirmed planning inputs, collected on 2026-09-20:

- The app should improve the desktop experience and organization of Databricks work. The user finds the web app unwieldy and wants fewer interruptions between analysis and desktop work.
- Target paid Azure Databricks used by developers at the user's company. Free Edition does not constrain the design, and success there would not establish company compatibility.
- Windows is the first implementation and validation target. The product must support Windows and macOS.
- Users should write notebooks and SQL queries inside the desktop app, choose compute, execute remotely, and see results in the app. The interaction should feel familiar on a desktop while retaining Databricks as the remote execution environment.
- Target environments include SQL warehouses, serverless notebook compute, and shared compute. The exact shared-compute access mode and runtime are not yet verified. These are desired targets, not established support claims.
- Workspace files and notebooks should be stored in Databricks. Exact remote-save, local buffering, and concurrent-edit behavior remain decisions.
- Volumes should work inside the app with browser-like file operations and easier drag-and-drop uploads from the desktop. The user has explicitly narrowed the earlier OneDrive analogy to this experience.
- A connection is required for remote work. During connection loss the app may retain visible content with a clear disconnected indication. Offline editing and synchronization are not first-version requirements.
- AI tooling integrations are out of scope while the user learns which desktop workflows need improvement.
- SSH is an experience analogy and a candidate integration mechanism, not a selected architecture. Shared compute makes an SSH-only assumption unsafe.
- Planning only. Do not build the application during this map. Research must distinguish documented capabilities, inference, and live verification.
- Consult wayfinder, grilling, domain-modeling, research for research tickets, and unslop. Tracker conventions are documented in the [tracker guide](../README.md).

## Decisions so far

- [Establish notebook execution support across Azure compute](002-notebook-execution.md): no public interface gives a uniform fully remote interactive notebook session across the desired compute types, so the product must expose capability differences and validate chosen paths in the company workspace.
- [Verify Azure workspace, SQL, and volume APIs](003-azure-interfaces.md): documented APIs cover authentication, discovery, warehouse SQL, notebook storage, and in-app volume transfers, subject to company policy, permissions, preview status, and live validation.

## Not yet specified

- A proof of the selected interactive notebook path, including kernel transport and lifecycle if the decision depends on SSH, can be specified after notebook behavior is chosen.
- Distribution and update constraints may become separate decisions after the desktop architecture and company installation policy are known.

## Out of scope

- Implementing or releasing the product in this planning effort.
- AI assistants, MCP integration, and direct orchestration by local coding agents in the first version.
- Explorer/Finder integration, mounted drives, OneDrive-style background synchronization, and full offline operation in the first version.
- Feature parity with the entire Databricks web application.
- Designing around Free Edition constraints or claiming compatibility based solely on Free Edition testing.
